# ReShade-HDR-Simulate-Oversaturation

[English](README.md) | [简体中文](README.zh-CN.md)

一个 ReShade 着色器,用来复现经典的"窄色域内容在未做色彩管理的广色域屏幕上直接显示"的观感——也就是很多人记忆里,早年色彩管理还不普及时,SDR 显示器上那种过饱和、很鲜艳的颜色。

和通用的饱和度/自然饱和度着色器不同,它不靠 HSV/HSL 去拉伸饱和度,而是复现这种效果背后真实的成因:把 HDR 管线正确显示的线性光当作 Rec.709/sRGB 数值,再把同样的三个数用**错误**的(更宽的)原色——Display P3 而不是 sRGB——重新解读。这正是显示器收到 sRGB 信号却不经转换、直接当作自己的原生广色域 RGB 时发生的事。

因为用的是真实的原色矩阵变换,红、绿、蓝三个通道是联动缩放的,所以黄色这类颜色会变得更浓,而不会出现简单的逐通道饱和度提升带来的色相偏移。它还是一个固定的线性变换,对任意亮度一视同仁——包括远高于 SDR 参考白的 HDR 高光——所以没有需要调的参考白参数,也不会损失高光细节。

只在 ReShade 后缓冲处于 HDR 色彩空间(scRGB 或 HDR10 PQ)时运行;在 SDR 下不起作用。

## 工作原理

1. 从 HDR 后缓冲解码像素(scRGB 本身就是线性的;HDR10 PQ 先解码为线性 BT.2020),并转换到 Rec.709 线性光。
2. 把这些数值按 Display P3 原色重新解读——这就是那个"bug"。
3. 按**效果强度**与原画面混合,混合在线性光中进行,因此滑块在 scRGB 与 HDR10 PQ 下含义一致。
4. 编码回显示器实际需要的输出格式。

整条链路已预合并成单个 3×3 矩阵,全部基于同一个 D65 白点(x = 0.3127,y = 0.3290)推导。每个矩阵的每一行之和都为 1,所以无彩色保持不变:黑还是黑,灰还是灰,白色保持精确的白。

## 参数

| 参数 | 说明 |
| ---- | ---- |
| **色彩空间判断方式** | `Auto` 使用 ReShade 在编译时检测到的色彩空间。如果你在游戏中开关 HDR 后效果不再响应,很可能是 ReShade 没能刷新色彩空间检测——手动切换为 `Force HDR10 PQ` 或 `Force scRGB` 即可(无需重启,像其他滑块一样立即生效)。`Force Off` 会完全关闭效果。强制选错模式会让画面显示异常,切回 `Auto` 或选对应的模式即可恢复。 |
| **效果强度 (%)** | 0 = 保持原色(正确颜色),100 = 完整效果。在线性光中混合。 |

## 安装

1. 把 `SimulateSRGBAsP3.fx` 放进 ReShade 的 shaders 文件夹(和你其他 `.fx` 文件放在一起)。
2. 在游戏内和 Windows 中开启 HDR。
3. 在 ReShade 界面中启用 `SimulateSRGBAsP3`。

如果你还在使用其他饱和度/调色着色器,请把本着色器放在效果列表的**最上方**(ReShade 自上而下处理),这样它处理的是其他调整叠加之前的颜色。

## 限制

- 假设游戏内容本来就是按 Rec.709/sRGB 色域制作的,绝大多数游戏如此。原生宽色域渲染的内容会显得过饱和。
- 输入不会被限制到 Rec.709,因此超出色域的颜色也走同一个线性变换。结果可能超出 Display P3,这部分颜色如何显示取决于你的显示器。在 HDR10 PQ 模式下,变成负值的分量无法被编码,会在最后一步被丢弃;scRGB 则会保留。
- 只有在色域比 sRGB 更宽的显示器上,效果才看得出来。
- 它处理的是最终画面,所以 UI、文字、HUD 的颜色也会受影响,不只是 3D 场景。
- 不支持 HDR10 HLG,会被视为"关闭"。
- `Auto` 的自动检测依赖 ReShade 在编译时正确报告 `BUFFER_COLOR_SPACE`。已知在同一次游戏中关闭再开启 HDR 后,这个值有时会过期——遇到这种情况请使用手动覆盖。
